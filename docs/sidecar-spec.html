01Summary

The sidecar treats World of Warcraft as a pixel source and nothing else. It captures the game's window through the OS, synthesises the inputs DLSS requires, runs the neural pass in its own process, and paints the result back over the game in a click-through overlay.

DLSS 5 is neural rendering, not upscaling — it re-lights and re-materialises surfaces, predominantly character models. WoW has no native DLSS of any kind, so there is no NGX call inside the game to intercept. Every published tool for enabling DLSS 5 solves that by injecting a ReShade add-on into the target process, which is precisely what cannot be done here.

So the neural pass moves out. The game process is never opened, never read, never written, never hooked. That constraint is the premise of the project, and every other decision on this page is subordinate to it.

02Why nothing off the shelf works

The DLSS 5 runtime — nvngx_dlssnr.dll, DLSSNR 310.8.0.0 — leaked on 26 August 2026 in an NBA 2K27 early-access build. Within hours the community had it running in Control, GTA 5 and Skyrim, and a patched build followed that fixes the incompatible CUDA instructions so it runs on Ada.

Every one of those tools works the same way: a ReShade add-on detours NVSDK_NGX_D3D12_CreateFeature and NVSDK_NGX_D3D12_EvaluateFeature and inserts the neural pass into the game's own DLSS call.

DLSS5-SwapperD3D12 games with native DLSSNo native DLSS
dlss5-dx11-bridgeD3D11 games with DLSS, via private D3D12 sessionNo native DLSS
DLSS5-FeederGames with no DLSS at all — synthesises a DLAA contractNeeds ReShade in-process
dlss5-d3d12-fixTypeless-to-typed output mismatchesInformative only
The actual blocker

Blizzard's Terms of Use prohibit third-party client modification and Warden enforces it. Patch 11.1.7 (14 July 2025) explicitly rejected ReShade's dxgi.dll, and Blizzard has issued ban waves and blue posts naming ReShade, with penalties up to permanent account closure. This is not a rendering problem. It is a process-boundary problem.

DLSS5-Feeder is architecturally the closest fit and is unusable for exactly one reason. This design takes its insight — synthesise the DLAA contract, run NGX on a private device — and relocates the whole thing outside the game.

03Safety model

The safety claim is made mechanical rather than asserted. A CI job dumps each binary's import table and fails the build on any forbidden symbol.

I1
No ReadProcessMemory, WriteProcessMemory, VirtualAllocEx, VirtualProtectEx or CreateRemoteThread in either binary's import table.
I2
OpenProcess never requested above PROCESS_QUERY_LIMITED_INFORMATION.
I3
SetWinEventHook used only with WINEVENT_OUTOFCONTEXT. The in-context form maps a DLL into the target and would destroy the premise.
I4
SetWindowsHookEx never used, in any form.
I5
Never write to WoW's install directory; never read WoW's game data. Display mode comes from GetWindowLong, not from parsing Config.wtf.
I6
Never synthesise input to WoW's window.
I7
The installer hard-refuses any target path containing Wow.exe, _retail_, _classic_ or _classic_era_.
I8
On every launch, enumerate filenames only in WoW's install directory for known injector loaders — dxgi.dll, d3d12.dll, dinput8.dll, version.dll, winmm.dll, opengl32.dll — and refuse to launch if any are found. Deliberately reads that directory, to stop the user being banned for something they did before installing this.
I9
The sidecar's own directory is re-verified at every launch to be outside WoW's install tree. I7 covers installation; I9 covers a user who moved things afterwards.
I10
No network connection, ever. No telemetry, no update check, no download. CI asserts no ws2_32, winhttp, wininet or urlmon imports. A tool that downloads DLLs onto a gamer's machine looks exactly like malware; this one cannot.
I11
The project distributes no third-party binaries — not the neural runtime, not the Ada patch, not ReShade. The user supplies them; we verify hashes and refuse unknown ones.
I12
Never behave the way a cheat behaves. No packing, no obfuscation, no anti-debug, no process-name randomisation, no elevation. Warden can see wowsidecar.exe in a process list and that is fine — what gets software flagged is looking like it is hiding.
I13
A panic hotkey hides the overlay and stops the pipeline instantly, without focus leaving the game.

Ban-risk analysis

Blizzard enforces against client modification and automation. Every vector they are known to act on is addressed by construction rather than by policy.

Enforcement vectorAppliesWhy
Code injected into Wow.exeNoI1–I4. Nothing of ours is ever loaded into the game process.
Client memory read or writtenNoI1, I2. We never open a handle capable of it.
Modified or added client filesNoI5, I7, I9. We never write to the install tree, and refuse to install into it.
Input automation, bottingNoI6. We never synthesise input. The sidecar cannot act.
Reading game state for advantageNoWe see only the pixels already on the player's screen, after the game drew them. No information the player did not already have.
Known-bad process signatureNoI12. We do nothing to hide, and we are not a cheat.
Screen capture of the game windowNot enforcedWGC is the same OS API behind OBS, Discord and Xbox Game Bar. Enforcing against it would ban most of the streaming population.
Residual risk, stated honestly

Blizzard could change what they enforce. This design removes every currently-known detection vector, which is the strongest position available — but it is not a guarantee, and nobody can offer one. If Blizzard's policy moves, the honest response is to stop shipping, not to evade.

The user can still ban themselves. The most plausible path to an account closure for someone holding this tool is putting ReShade next to Wow.exe on their own initiative. I7 makes that awkward at install time and I8 makes it blocking at launch time, but a determined user can still do it.

The project claims what it can support: this sidecar does not do any of the things Blizzard bans people for. It does not claim that installing it is risk-free, because that claim would not be true of any third-party tool.

Failure rule — outranks everything else

On any pipeline failure, hide the overlay immediately. This is an opaque window covering a live game; a broken pipeline that keeps presenting leaves the player blind mid-encounter. Fail to a visible game, never to black.

04Architecture

One runtime executable plus one manager. Three threads in the runtime: capture (WinRT GraphicsCaptureItem on a D3D11 device, free-threaded frame pool), render (owns the D3D12 device — flow, neural pass, present), and control (hotkeys, config, window tracking, HUD).

The D3D11-to-D3D12 seam

WGC produces D3D11 textures; NGX and NVOFA consume D3D12 resources. Two devices are created on the same adapter, matched by LUID, bridged by a three-deep ring of SHARED_NTHANDLE textures opened with OpenSharedHandle. Synchronisation uses a shared fence pair. A keyed mutex is explicitly rejected — it serialises the two queues and costs latency the budget cannot absorb.

Presentation

WS_EX_LAYERED cannot host a flip swapchain, so the overlay is a WS_POPUP with WS_EX_NOREDIRECTIONBITMAP | WS_EX_TRANSPARENT | WS_EX_NOACTIVATE | WS_EX_TOPMOST, a DirectComposition visual tree, and CreateSwapChainForComposition at SetMaximumFrameLatency(1). WS_EX_TRANSPARENT gives click-through; WS_EX_NOACTIVATE keeps WoW focused so it never drops to its background frame limit.

Two modules carry disproportionate risk

FlowToMotionVec — NVOFA emits S10.5 fixed-point flow whose direction is configuration-dependent, while NGX expects pixels or NDC governed by MV_Scale_X/Y. A wrong sign or scale produces smearing under motion: a failure that presents as a quality problem rather than a bug, and can therefore survive undiagnosed for a long time. It gets a unit test against synthetic pairs with known translation before it ever sees WoW.

FormatNormalize — the existence of dlss5-d3d12-fix, which exists solely to correct typeless-to-typed mismatches, tells us the add-on is sensitive to resource formats. We normalise to R16G16B16A16_FLOAT with explicitly typed views on both ends.

05Frame pipeline and pacing

Pacing rule

If the render thread is busy when a new capture arrives, the pending slot is overwritten, never queued. Queuing converts a transient hitch into permanent latency growth that never recovers. Latest frame wins; drops are counted and shown in the HUD.

Honest scope. This suits questing, exploration, roleplay and screenshots. It does not suit Mythic+, raid progression or arena. The manager says so in plain words rather than burying it.

The neural runtime is user-supplied and verified by SHA-256 against a manifest covering both variants. An unknown hash is refused with a readable message rather than an access violation at feature creation. Nothing unredistributable enters the repository.

07Neural pass routes

INeuralPass abstracts how the neural pass is invoked. Three implementations, shipped in this order.

ImplementationMechanismTradeStatus
PassthroughPass Copies input to output, no NGX at all. Lets the whole real-time pipeline be validated before any unredistributable binary is involved. Also the permanent fallback. M0
ReshadeHostedPass Our own D3D12 device and NGX session; ReShade loaded into our process so renodx-dlss5 detours our evaluate call. Depends on a closed-source community binary and inherits ReShade's lifecycle — both acceptable, since neither touches WoW. Proven to work today. Primary
DirectNgxPass Create the neural-rendering feature directly on our own NGX session. No detour, no ReShade, no third-party binary. Feature ID and parameter contract are undocumented and need export-table reverse engineering. May not be callable standalone at all. M6, speculative

Route B ships first because it is the route proven to work. If route A cracks, this becomes the first DLSS-NR implementation with no ReShade dependency anywhere and route B is dropped. If it does not, route B already shipped and nothing was wasted.

08UI masking

WoW's interface is composited into the captured frame and no API exposes a mask for it. Left alone, the neural pass will treat action bars and nameplates as material to re-render. This is the largest quality risk in the project.

A purely temporal heuristic was considered and rejected as the primary mechanism. Instead: a one-time calibration where the user drags rectangles over their action bars, unit frames, chat and minimap, stored in config. WoW interfaces are static per user, so this is close to exact for the large majority of screen-space UI at zero runtime cost.

A temporal-stability and edge-energy heuristic then handles only the moving remainder — nameplates and floating combat text. Original pixels are blended back wherever the combined mask indicates interface. v1 ships the config plumbing and blend path with an empty rectangle list.

09Manager application

wowsidecar-manager.exe — Dear ImGui on D3D11, custom-themed, borderless window with its own title bar. Same toolchain as the runtime, no additional runtime prerequisite for the user, single executable. WinUI 3 was considered and rejected: a more native feel is not worth a second toolchain and a .NET dependency for this audience.

Actions

  • Install — place user-supplied DLLs into the sidecar directory, write config.
  • Remove — delete everything created, verifiably clean.
  • Launch / Stop — with a live HUD showing capture-to-present p50 and p99, plus dropped frames.
  • Calibrate — paint the UI mask rectangles.
Two safety behaviours that are product features, not disclaimers

Per I7, the installer hard-refuses any target path containing a WoW install signature. The most plausible route to a ban for a user holding this tool is placing ReShade next to Wow.exe themselves, so the installer makes that physically awkward.

A first-run notice, acknowledged once, states the boundary plainly: this sidecar never loads code into Wow.exe, which is what makes it safe; ReShade pointed at Wow.exe is a bannable offence Blizzard actively enforces; and the tool will not help with that.

10Testing

testpattern.exe is the highest-value item here — a trivial D3D window rendering known geometry, shipped with the project, that lets the entire capture, bridge, overlay and pacing path be verified pixel-exact with neither WoW nor NGX involved.

  • Unit — FlowToMotionVec against synthetic pairs with known translation; FormatNormalize round-trip; config parsing; hash manifest matching.
  • CI invariants — dumps both binaries' import tables and fails the build on any symbol forbidden by I1–I4, and on any networking import forbidden by I10. A second job asserts I12: binaries unpacked, unobfuscated, no elevated manifest. This is what converts the safety claim from an assertion into a check.
  • Latency instrumentation — HUD reporting capture-to-present p50/p99 and dropped-frame count, which is the evidence for the M1 gate.

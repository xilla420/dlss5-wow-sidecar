# DLSS 5 Sidecar — M3 to M6 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Get DLSS 5 Neural Rendering actually running on captured World of Warcraft frames, select the right runtime per GPU architecture, stop the neural pass from chewing up the game's interface, and — if the contract cracks — drop the third-party dependency entirely.

**Predecessor:** [`2026-08-30-sidecar-m0-m2.md`](2026-08-30-sidecar-m0-m2.md), complete. Do not restate its constraints; they all still bind.

## What M0–M2 established, measured

This plan exists because the M1 decision gate passed. The numbers it passed on, on an RTX 4080 (Ada) against live WoW Retail at 2560×1440 borderless windowed:

| Configuration | p50 | p99 | Drops | Verdict |
|---|---|---|---|---|
| Capture → passthrough → present | 0.6 ms | 2.3 ms | 0 | playable |
| The same, with optical flow active | 2.6 ms | 6.1 ms | 0 | playable |

The gate was "stop and reconsider above roughly 80 ms". Actual p99 is **6.1 ms**, roughly thirteen times under it. Live overlay is the product; photo mode is not needed.

Also established and verified on hardware:

- The D3D11→D3D12 shared-texture bridge transfers pixel-exact.
- The overlay is click-through: it answers `HTTRANSPARENT` to `WM_NCHITTEST` asked from a third process.
- WGC capture of an occluded window under an always-on-top overlay works — spec §17's flagged risk, now retired.
- NVOFA returns **−4.5 px** against the test pattern's known **+4 px/frame** motion. Right magnitude, and negative, which confirms NVOFA reports where a pixel came *from* and that `FlowToMotionPixels`' negation is the correct direction. This was the spec's largest single correctness risk (§8, "two modules that carry disproportionate risk") and it is now measured rather than assumed.
- `nvofapi64.dll` is resolved with `LoadLibrary`, so it never enters the import table and the binary loads without it.

**What is built but inert, and becomes live in this plan:**

| Thing | State today | Becomes live in |
|---|---|---|
| `normalized_` (RGBA16F) | written every frame, read by nothing | M3 — it is the neural pass's colour input |
| `motionTarget_` (RG16F, NDC) | written when flow runs, read by nothing | M3 — it is the motion input |
| `Config::uiMaskRects` | parsed, no consumer | M5 |
| `ProbeNeuralRuntime` | presence check only, no hash | M4 |
| `INeuralPass::depth` | always `nullptr` | **see Task 3 — may stay `nullptr` forever** |

## Additional constraints for this plan

Everything in the M0–M2 plan's Global Constraints still applies without change. On top of them:

- **No third-party binary is ever committed, downloaded automatically, or redistributed.** `nvngx_dlssnr.dll`, the community Ada build, ReShade, and `renodx-dlss5.addon64` are all **user-supplied**. `.gitignore` already blocks `*.dll`, `*.exe`, `*.addon64`, `*.addon32`. The manager tells the operator what to fetch and where to put it; it never fetches anything (I10 — no networking, in either binary).
- **The neural pass is never on the critical path for correctness.** Every failure — missing runtime, bad hash, failed feature creation, failed evaluate — degrades to `PassthroughPass` and says so. This is spec §11 and it is already how `MakeNeuralPass` behaves.
- **The failure rule still outranks everything.** Any pipeline failure hides the overlay before doing anything else.
- **Config is live.** As of the M0–M2 follow-up work, `wowsidecar.exe` reads `sidecar.toml` and honours `neural_pass`, `flow_grid_size`, `show_hud` and `show_overlay`. New settings go through `Config` and get a unit test, not an ad-hoc parse.

## The two questions M3 must answer before anything else is worth building

The spec is honest that route A is speculative. It is less explicit about a problem that applies to **both** routes, and this plan puts it first because everything downstream depends on the answer.

### Question 1: there is no depth buffer, and there cannot be one

DLSS5-Feeder — the closest prior art, and the thing this design relocates — synthesises its DLAA contract from **ReShade's depth buffer plus estimated motion**. It runs inside the game process, so it has the game's depth.

This sidecar captures the final composited frame from DWM, out of process. There is no depth buffer, no albedo, no normals, no camera matrices. There is exactly one colour image and a motion field estimated from two consecutive colour images.

So the contract available to us is strictly weaker than the one every published tool uses. Task 3 is a spike that answers, on real hardware: does the NR feature accept a colour+motion contract with depth absent or synthesised constant, and if so what does the output look like? **If the answer is no, M3 as specified does not ship**, and the honest fallback is to reconsider what the pass can be given a colour-only contract. Finding that out costs one spike and is far cheaper than discovering it at the end of a two-week implementation.

### Question 2: does the detour even fire in our process?

Route B's premise is that ReShade loaded into *our* process lets `renodx-dlss5.addon64` detour *our* NGX calls. The add-on was written to detour a game. It may assume a swapchain presenting to a visible window, a particular device creation order, or a graphics API surface we do not present. Task 4 verifies the detour fires before any pipeline integration is attempted.

## Task 1: Pay off the device-loss threading debt

Carried over from M0–M2 and still unfixed. `Pipeline::Rebuild()` runs on the render thread and calls `Pipeline::Create`, which calls `CreateWindowExW` for the overlay. The render thread has no message pump, so the rebuilt overlay's window belongs to a thread that will never service it. `Hide()` survives this (it is `SWP_ASYNCWINDOWPOS`), but `Show()` and `SetBounds` will not behave.

This is fixed first because M3 makes device loss *more* likely, not less: a neural pass is exactly the kind of workload that provokes TDR.

**Files:** modify `src/runtime/Pipeline.h/.cpp`, `src/runtime/main.cpp`. Test: `tests/test_pipeline_rebuild.cpp`.

- [ ] **Step 1:** Write a `[device]` test that drives `Rebuild()` directly on a pipeline running against `testpattern.exe`, then asserts the overlay is visible, correctly positioned, and still presenting afterwards. This currently fails or hangs; that is the point.
- [ ] **Step 2:** Move window ownership to the thread that pumps. The render thread signals "rebuild needed" through an atomic; `wWinMain`'s message loop observes it, performs the rebuild on the UI thread, and restarts the render thread. Rebuilding is a rare, already-catastrophic path — a thread restart costs nothing there and removes a whole class of cross-thread window bugs.
- [ ] **Step 3:** Verify the test passes, including that `LastError()` reports the reset and the HUD keeps painting (`Hud::Create` points a file-scope pointer at the newest instance; the M0–M2 `Rebuild` already transfers it, and that must survive the restructure).
- [ ] **Step 4:** Commit.

## Task 2: The logging module the first plan listed and never built

Config warnings currently go to `OutputDebugString`, which is invisible to an operator without a debugger. Everything in M3 onward — hash mismatches, feature-creation failures, detour status — produces diagnostics that a user has to be able to read and paste into a bug report.

**Files:** create `src/common/core/Log.h/.cpp`. Test: `tests/test_log.cpp`.

- [ ] **Step 1:** Failing tests: the ring buffer keeps the last N lines and drops the oldest; levels filter; formatting is stable; the ring never allocates after construction (it is read by the HUD on the render thread).
- [ ] **Step 2:** Implement. File sink next to the executable, plus a fixed-capacity in-memory ring the manager and HUD can read. No timestamps from `localtime` on the render thread — precompute.
- [ ] **Step 3:** Route existing diagnostics through it: `Config` warnings, `Pipeline::FailAndHide` reasons, `NvofaFlow` unavailability, `MakeNeuralPass` fallbacks.
- [ ] **Step 4:** Surface the last error in the manager's dependency board.
- [ ] **Step 5:** Commit.

## Task 3: Spike — what contract does the NR feature actually accept?

**This is a throwaway spike in `tools/spike_ngx/`. It is not shipped, not linked into `sidecar_common`, and is deleted or archived when the question is answered.** Its only output is a written answer in the commit message and a decision about whether Task 5 proceeds as specified.

- [ ] **Step 1:** Stand up a minimal D3D12 NGX session in a console app: `NVSDK_NGX_D3D12_Init`, capability query, feature creation. Report exactly which NGX entry points `nvngx_dlssnr.dll` exports, and what the driver reports for `Enable DLSS NR Override`.
- [ ] **Step 2:** Attempt feature creation for neural rendering. Record the feature identifier, the required parameter names, and every failure code verbatim.
- [ ] **Step 3:** **The depth question.** Evaluate with (a) real colour + estimated motion + no depth, (b) the same + a constant-depth texture, (c) the same + a depth texture derived from luminance as a crude proxy. Record which are accepted and what each produces. Capture output frames for visual comparison.
- [ ] **Step 4:** Write the answer down. If no colour+motion contract is accepted, **stop and revise this plan** rather than proceeding to Task 5. Say so plainly in the commit; a negative result here is a successful spike.
- [ ] **Step 5:** Commit the findings (and the spike harness, since M6 will want it back).

## Task 4: Spike — does the ReShade detour fire in our process? ✅ **yes**

- [x] **Step 1:** Load ReShade into the spike harness alongside `renodx-dlss5.addon64`.
- [x] **Step 2:** Instrument our own `NVSDK_NGX_D3D12_EvaluateFeature` call and observe whether the add-on's detour is invoked.
- [x] **Step 3:** If it does not fire, determine why. It fires. ReShade attaches to the composition swapchain, the add-on detours six NGX entry points across the core and the DLSS snippet, and it intercepts our own create and evaluate.
- [x] **Step 4:** Commit the findings.

**Answered further than asked.** The add-on also initialises `nvngx_dlssnr.dll` inside our
process and attempts `CreateFeature(18)`, which fails with plain `Fail` (`0xbad00001`). Two
candidate causes, not yet separated: a rejected contract (the spike's inputs were synthetic and
depth was uninitialised), or the stock NR runtime declining to run on Ada — which is what Task 6
already assumes when it gives Ada a patched variant. **Separating them needs the Ada runtime
variant, which is operator-supplied.**

## Task 5: `ReshadeHostedPass` — M3

Tasks 3 and 4 have now answered, and they change this task's shape:

- **The sidecar must create and evaluate a real DLSS feature.** The add-on activates on nothing
  else — it harvests the colour/depth/motion contract from an intercepted DLSS create, then runs
  NR on that. `ReshadeHostedPass` is therefore a DLSS client whose output the add-on replaces, not
  an NR client. This is the assumption Task 3 corrected and Task 4 confirmed on hardware.
- **Depth is required, not optional.** The add-on reads `DLSS.Input.Depth.*` from our parameter
  block. Question 1 is still unanswered and is now squarely inside this task.
- **`NgxSession` must resolve its feature search path to an absolute path.** A relative one
  silently finds no runtimes and reports as `SuperSampling.Available = 0`, which is
  indistinguishable from an unsupported driver. This cost a wrong reading during Task 4.
- **Step 2 has a real digest to start from:** `nvngx_dlssnr.dll` 310.8.0 is
  `E16BCF15E16E13F527491CDF7845B2FE6521A738D8F7C9C721866A8496E1FC8E`.

Build order is deliberate: the runtime manifest comes first so that a wrong binary is refused with a readable message rather than an access violation at feature creation (spec §10).

**Files:** create `src/common/core/Sha256.h/.cpp`, `src/common/neural/RuntimeManifest.h/.cpp`, `src/common/neural/NgxSession.h/.cpp`, `src/common/neural/ReshadeHostedPass.h/.cpp`. Modify `NeuralPassFactory.cpp`, `Pipeline.cpp`, `Probes.cpp`.

- [x] **Step 1:** `Sha256` over Windows CNG, against the published NIST vectors plus a million-byte input that forces incremental hashing. `Sha256File` streams in 1 MiB chunks, because the runtime is ~166 MB.
- [x] **Step 2:** `RuntimeManifest`. Seeded with the one build observed on hardware (310.8.0, stock). Lookup is case-insensitive and rejects anything not digest-shaped; `DescribeRuntime` names the file and its actual digest for an unknown build. `VariantForArchitecture` pins the Task 6 matrix.
- [x] **Step 3:** `ProbeNeuralRuntime` now hashes. The decision is split into a pure `NeuralRuntimeVerdict(fileName, digest)` so the *recognised* path is testable — a file that hashes to a manifest entry cannot be produced on demand. Unknown is amber with the digest, never red.
- [x] **Step 4:** `NgxSession`, gated on `DLSS_SDK_DIR` exactly as `NvofaFlow` is on `NVOF_SDK_DIR`; without it, a stub that reports why. Linking `nvsdk_ngx_d.lib` adds **no DLL import** — verified against `ci/check_imports.py` on both the spike and the shipped binaries — so the sidecar still loads on a machine with no NGX core. The search path is forced absolute inside `Create`.

  Also corrected here: `ProbeReshade` looked for `ReShade64.dll`, which a real install never produces. ReShade installs as a proxy named after the API the host imports — `dxgi.dll` for this sidecar — so that probe had never once found a genuine install.
- [ ] **Step 5:** `ReshadeHostedPass implements INeuralPass`. `Evaluate` binds `normalized_` as colour, `motionTarget_` as motion, depth per Task 3's answer, and writes the work target. Returns `false` on any failure so the pipeline falls back; never throws.
- [ ] **Step 6:** Register it in `MakeNeuralPass` under `"reshade"`, replacing the current "not implemented yet" warning. The factory's existing unit tests change to assert the new behaviour.
- [ ] **Step 7:** Wire `normalized_` and `motionTarget_` into `pass_->Evaluate` in `Pipeline::RenderLoop`. They are already produced every frame; this is the first time anything reads them.
- [ ] **Step 8:** Device test against `testpattern.exe`: with the pass active, output differs from input (the pass ran) but the frame is not black, not NaN, and the quadrant colours remain recognisable.
- [ ] **Step 9:** **Measure against live WoW and record p50/p99/drops in the commit message**, exactly as M1 did. Compare against the 2.6/6.1 ms baseline. The spec warns the pass may be too expensive on Ada (§17); this is where that is settled. If p99 crosses 80 ms, say so and reconsider before continuing.
- [ ] **Step 10:** Commit — M3 complete.

## Task 7: UI mask arithmetic — pure, unit-tested

The spec calls UI masking "the largest quality risk in the project" (§12). As with the motion-vector conversion, the arithmetic is split into a pure function so it is testable without a GPU, and the shader is written to match it.

**Files:** create `src/common/gpu/MaskMath.h`. Test: `tests/test_mask_math.cpp`.

- [ ] **Step 1:** Failing tests: a point inside a rectangle is masked; on the boundary the rule is stated and pinned (half-open, matching `RECT` convention); overlapping rectangles union rather than double-count; rectangles are clamped to the frame; an empty list masks nothing; rectangles expressed at one resolution scale correctly to another, because the operator calibrates at their desktop resolution and the pass may run at a different internal one.
- [ ] **Step 2:** Implement as `constexpr` where possible.
- [ ] **Step 3:** Commit.

## Task 10: `DirectNgxPass` — M6 — **closed, with the reason recorded**

Both doors were tested and both are shut, for different reasons:

| door | harness | result |
|---|---|---|
| NGX core feature registry | `spike_ngx` | ids ≥ 18 `OutOfDate`; no SDK version above `0x15` gets past `Init` |
| `nvngx_dlssnr.dll`'s own exports | `spike_snippet` | `Init_Ext` → `PlatformError`, `Init` → `FeatureNotSupported`, invariant across six versions |

The barrier is not that NR is unreachable to call — it is that the runtime declines a session set
up by anyone but the NGX core. Step 4 below is therefore the outcome, and it is the one the spec
planned for. This reopens only if NVIDIA ships an SDK this core accepts that also names the
feature.

- [x] **Step 1:** From the spike findings, attempt feature creation and evaluation with no ReShade and no add-on in the process at all. Done in `spike_snippet`; refused.
- [ ] **Step 2:** If it works: implement `DirectNgxPass`, register it as `"ngx"`, and make it the default where the runtime hash is recognised.
- [ ] **Step 3:** If it works, ReShade and the add-on drop out of the prerequisites table entirely and the manager stops probing for them.
- [ ] **Step 4:** If it does not work, record precisely why and close M6 as "not possible with this runtime version". Route B already shipped; nothing is wasted. That is the outcome the spec explicitly planned for.
- [ ] **Step 5:** Commit.

## Definition of done

- **M3:** DLSS 5 NR runs on live WoW frames through `ReshadeHostedPass`, latency measured and recorded, and every failure path falls back to passthrough with a readable log line.
- **M4:** The correct runtime variant is selected automatically per architecture, hash-verified, and named on screen.
- **M5:** An operator can calibrate their interface once and the neural pass leaves it alone thereafter.
- **M6:** Either ReShade is gone, or there is a written account of why it cannot be.
- Throughout: `[unit]` passes with no GPU, `[device]` passes on the target machine, CI stays green, and all three binaries keep passing the import-table check.

## What this plan deliberately does not cover

- **Frame generation.** DLSS 5 NR re-lights and re-materialises; it does not interpolate frames. Motion vectors exist here to satisfy the DLAA contract, not to synthesise frames. Frame generation from an out-of-process capture is a different project with a different latency budget.
- **The nameplate heuristic**, until the rectangle mask has been measured in practice (Task 9).
- **Distribution and installers.** Nothing here is redistributable, so there is nothing to package.
- **Supporting RTX 20/30.** The spec refuses them and `GpuProfile` already does.
